# My Recipes — Project Specification

## 1. Overview

A private recipe-management web app for a small circle of users (family/friends). Each user has an
account and can create, organize, and share recipes with the rest of the circle. Includes recipe
scaling/unit conversion, tag-based search, a weekly meal planner, shopping-list generation, and
recipe import from a URL — including YouTube videos — with manual entry as an alternative.

Single language (no i18n). Self-hosted via Docker, following the same architecture as
`yarg-aggregator` (Redis/BullMQ dropped — no background job queue needed for this project).

## 2. Tech Stack

Mirrors `yarg-aggregator`, minus the job-queue layer:

- **Framework**: Next.js (App Router), React 19, TypeScript (strict mode)
- **Styling/UI**: Tailwind CSS 4, Shadcn UI (Radix primitives), `lucide-react` icons
- **Database**: PostgreSQL with Drizzle ORM
- **Auth**: Better Auth — email/password + Google OAuth
- **Recipe extraction**: `schema.org/Recipe` JSON-LD parsing first (no LLM), then LLM fallback via
  OpenRouter SDK (or equivalent) server-side; opportunistic in-browser inference (Chrome's
  on-device Prompt API) as an optimization when available
- **YouTube**: YouTube Data API v3 (video metadata/description) and `youtubei.js` (Innertube) for
  caption/transcript fetching — no audio/video processing on the server
- **Image handling**: `sharp` for resizing/optimizing uploaded photos
- **Deployment**: Docker + docker-compose (app + Postgres containers), `Dockerfile`, `deploy.sh`,
  matching yarg's self-hosted pattern
- **No Redis / BullMQ / job queue** — all work (including LLM import) runs synchronously in the
  request lifecycle

## 2a. Visual Design & UI Quality

The interface is a first-class feature, not an afterthought. Target the design quality of a
polished consumer product (think Linear, Notion, or a premium editorial cooking site — NYT
Cooking) rather than an internal tool or a default-shadcn admin dashboard.

- **Overall feel**: modern, elegant, warm, and inviting — this is an app about food, so it should
  feel appetizing. Food photography is the hero: recipe images displayed large and beautifully,
  never cramped into small thumbnails.
- **Craft**: a deliberate, cohesive design system — refined typography with a clear hierarchy (a
  distinctive display face for recipe titles paired with a highly readable body face), a
  purposeful color palette with warm accents, generous whitespace, consistent spacing rhythm, and
  soft, tasteful depth (subtle shadows/rounded corners, no heavy borders).
- **Delight**: smooth micro-interactions and transitions (hover states, drag feedback in the meal
  planner, satisfying check-off animation in the shopping list) — subtle and fast, never gratuitous.
- **Avoid the generic-AI look**: no boilerplate hero sections, no cookie-cutter card grids with
  identical gray borders, no default component styling left untouched. Every screen should look
  intentionally designed.
- **Responsive**: gorgeous on mobile — the kitchen is a primary use context. Recipe detail and
  shopping list must be excellent one-handed, on a small screen, with big touch targets.
- **States matter**: designed empty states (first recipe, empty planner, empty list), loading
  skeletons, and friendly error states — no blank white screens or raw spinners.

## 3. User Model & Auth

- Multi-user, invite/closed circle. **Enforced**, not just implied: Better Auth's default open
  signup is disabled; new accounts require a single-use invite code generated by an existing
  member (applies to both email/password and Google OAuth sign-ups).
- Better Auth handles sessions with two sign-in methods: email/password and Google OAuth.
- All authenticated users see the same shared recipe collection (a "circle"), each recipe tagged
  with its author.
- Any circle member can view/edit/scale any recipe; ratings and notes are private per-user.
- Deletion: only the recipe's author can delete it; deletes are soft (a `deletedAt` timestamp) so
  accidental deletions are recoverable from the database.

## 4. Core Features

### 4.1 Recipes (CRUD)
- Title, description, servings, prep/cook time, categories, tags, ingredients list, step-by-step
  instructions, one or more photos.
- Instructions are stored as a structured list of steps (not one text blob) — this enables
  step checkboxes ("cook mode"), per-step durations, and optional per-step video timestamps
  without a migration. Each step: `{ text, durationMinutes?, videoTimestamp? }`.
  `durationMinutes` is extracted by the LLM importer when a step contains a duration ("bake for
  25 minutes") and editable in the form — it feeds kitchen timers (see §9).
- A **"Send to kitchen"** action on the recipe detail page marks the recipe (with its current
  scaling) as the circle's active kitchen recipe — the target that cook mode and the future
  Alexa skill (§9) resume by default.
- Optional `sourceUrl` (where the recipe was imported from / attribution) and `videoUrl`
  (YouTube link, whether or not the recipe was imported from it).
- Recipes with a `videoUrl` show an embedded YouTube player on the detail page, using the
  `lite-youtube-embed` pattern (thumbnail placeholder; the heavy iframe loads only on click).
- Author + created/updated timestamps.

### 4.1a Cook Mode
- Full-screen, distraction-free step-by-step view, entered from the recipe detail page (and the
  target of "Send to kitchen" / the future Alexa skill, §9).
- One step at a time, in large type readable from arm's length; big next/back touch targets and
  a step progress indicator; steps can be checked off.
- Ingredients (scaled to the selected servings) accessible at a glance without leaving the view
  — e.g. a collapsible panel alongside or below the current step.
- **Screen wake lock** via the Screen Wake Lock API (`navigator.wakeLock`) so the display never
  sleeps mid-recipe; released on exit, re-acquired on the `visibilitychange` event when the user
  switches back to the tab (the browser auto-releases it on tab switch).
- If a step has `durationMinutes`, show an inline start-timer button with an on-screen countdown
  (browser timer — device-native timers remain the Alexa skill's job, §9).
- Progress syncs to `KitchenState.currentStepIndex` when the recipe is the active kitchen recipe,
  so web cook mode and the future Alexa skill stay on the same step.

### 4.2 Categories & Tags + Search
- Free-form tags (e.g. cuisine, diet, meal type) plus a fixed set of categories (e.g. Breakfast,
  Main, Dessert). The category list is seeded via a Drizzle seed script on first deploy.
- Search/filter by text query, tag, category, and ingredient.
- Text search is plain `ILIKE` over title/description/ingredient names — adequate at this scale;
  no full-text-search (tsvector) infrastructure in v1.

### 4.3 Scaling & Unit Conversion
- Adjust servings on a recipe view; ingredient quantities scale proportionally.
- Metric units only (grams, ml, °C, etc.) — no imperial conversion needed.
- Quantities are stored as nullable decimals: unquantified ingredients ("salt, to taste") have no
  quantity and are excluded from scaling.
- Scaled quantities display fraction-friendly where sensible (1.33 eggs → "1⅓ eggs"); weights/
  volumes round to practical precision (e.g. 267 g, not 266.67 g).

### 4.4 Meal Planning
- Simple weekly calendar view (breakfast/lunch/dinner slots per day).
- The meal plan is **circle-shared** (one family calendar), consistent with the shared recipe
  collection — not per-user.
- Drag/assign recipes onto calendar slots.

### 4.5 Shopping Lists
- Generate a shopping list from one or more planned meals / selected recipes.
- Merge duplicate ingredients across recipes (e.g. 2×"200g flour" → "400g flour").
- Merging requires the same canonical ingredient **and** compatible units; incompatible units
  (200 g flour + 2 tbsp flour) stay as separate lines grouped under the same ingredient heading.
- Manually check off / edit items.

### 4.5a Ingredient Canonicalization
- The `Ingredient` table holds one canonical row per real-world ingredient; `RecipeIngredient`
  rows reference it. This is what makes search-by-ingredient and shopping-list merging work.
- Matching rule on save/import: normalize the name (lowercase, trim, singularize), look up an
  existing `Ingredient`, auto-create on miss.
- LLM extraction is instructed to split each ingredient line into `ingredient` ("tomato"),
  `quantity`/`unit`, and `note` ("chopped") so preparation details never pollute canonical names.

### 4.6 Recipe Import from URL
- User pastes a recipe URL. If it's a YouTube URL, the flow branches to 4.6b; otherwise the
  extraction pipeline is, in order:
  1. **`schema.org/Recipe` JSON-LD** — most recipe sites embed structured recipe data (the same
     markup Google's recipe cards use). Parsing it is deterministic, instant, and free; expected
     to cover the large majority of URLs with no LLM call at all.
  2. **LLM extraction (server-side, primary fallback)** — the server fetches the page, strips it
     to readable text, and calls OpenRouter to parse title, servings, ingredients, and steps into
     the recipe schema.
  3. **In-browser inference (opportunistic optimization)** — if the user's browser exposes
     Chrome's on-device Prompt API (desktop Chrome only, requires the Gemini Nano model to be
     downloaded), extraction may run locally instead of step 2. The page HTML is still fetched
     through a small server proxy endpoint — client-side fetching of arbitrary sites is blocked
     by CORS — only the inference itself is local. If unavailable or it produces invalid output,
     fall back to step 2.
- The `sourceUrl` is stored on the resulting recipe.
- Extracted recipe is shown as an editable draft before saving.
- Operational constraints for the import endpoint (the one route that spends money per call):
  explicit route `maxDuration` (LLM extraction can take 30–60 s) with a client-side progress
  state, and per-user rate limiting. If gateway/proxy timeouts ever become a problem, the escape
  hatch is a simple `import_jobs` table polled by the client — async behavior without Redis.

### 4.6b Recipe Import from YouTube
- User pastes a YouTube URL (`youtube.com` / `youtu.be`), either via the same import box as 4.6
  or directly on the recipe form.
- No video or audio is ever downloaded or processed on the server — extraction uses text YouTube
  already has, cheapest source first:
  1. **Video description** — many cooking channels paste the full recipe there. Fetched via the
     YouTube Data API v3 (free quota, API key only); run through the same LLM extraction as 4.6.
  2. **Captions/transcript** — if the description yields no recipe, fetch YouTube's own captions
     (auto-generated ones exist for most videos) via `youtubei.js` (Innertube, no API key
     needed) and run LLM extraction over the transcript. A 10-minute video is ~1,500–2,000
     words, so the LLM call stays small and cheap.
  3. If neither yields a usable recipe, tell the user and open manual entry (4.6c) with
     `videoUrl` and title pre-filled from the video metadata.
- Transcripts often narrate imprecise quantities ("a good glug of oil"); the draft UI flags
  quantities the LLM inferred rather than read verbatim, so the user can verify them.
- YouTube import is server-side only (caption/description fetching is cross-origin, so the
  in-browser Prompt API path from 4.6 doesn't apply).
- The video URL is stored as `videoUrl` (embedded player per 4.1) and also as `sourceUrl`.

### 4.6c Manual Recipe Entry
- User can add a recipe entirely by hand via a form (no URL/LLM involved), using the same
  create/edit UI as the editable draft from URL import.
- Same schema and validation as imported recipes: title, servings, prep/cook time, categories,
  tags, ingredients, steps, photos.

### 4.7 Ratings & Personal Notes
- Each user can rate a recipe (e.g. 1–5 stars) and attach private notes (e.g. "used less salt")
  visible only to themselves.
- No shared/circle-visible comments in v1.

### 4.8 Images
- Recipe photos uploaded and stored on local disk / Docker volume (no external object storage).
- Resized/optimized via `sharp` on upload.
- Limits: JPEG/PNG/WebP/HEIC input, max 10 MB per upload, max 6 photos per recipe; stored as WebP
  at capped dimensions (e.g. 1600px longest edge) plus a thumbnail.

### 4.9 Backup Export
- A "Download backup" action (settings page) available to any circle member — one click produces
  a complete, restorable snapshot the user can drop into Google Drive or anywhere else.
- `GET /api/backup` streams a `my-recipes-backup-YYYY-MM-DD.tar.gz` containing:
  - `db.dump` — `pg_dump` in custom format (`-Fc`, compressed, restorable with `pg_restore`)
  - `uploads/` — the recipe photo files from the image volume
- Implementation: the route spawns `pg_dump` (pointed at `DATABASE_URL`) and pipes its stdout,
  together with the uploads directory, through a tar/gzip stream directly into the response — no
  temp files, no size limit surprises. Requires the `postgresql-client` package (matching the
  Postgres major version) in the app's Docker image.
- Restore path documented in the README: `pg_restore` the dump, copy `uploads/` back into the
  volume.
- Auth-protected like every other route; no rate limiting beyond login, but exports are logged.

## 5. Data Model (draft)

- `User` — id, name, email, image, auth fields (managed by Better Auth)
- `InviteCode` — id, code, createdByUserId, usedByUserId, createdAt, usedAt (single-use)
- `Recipe` — id, authorId, title, description, servings, prepTime, cookTime,
  steps (jsonb array: `{ text, durationMinutes?, videoTimestamp? }`), sourceUrl, videoUrl,
  createdAt, updatedAt, deletedAt (soft delete)
- `RecipeImage` — id, recipeId, path, order
- `Ingredient` — id, name (canonical: lowercased, singularized; unique)
- `RecipeIngredient` — id, recipeId, ingredientId, quantity (decimal, nullable), unit, note, order
- `Category` — id, name (fixed set, seeded)
- `Tag` — id, name
- `RecipeCategory` / `RecipeTag` — join tables
- `Rating` — id, userId, recipeId, score
- `Note` — id, userId, recipeId, body (private)
- `MealPlanEntry` — id, date, slot (breakfast/lunch/dinner), recipeId, addedByUserId
  (circle-shared — see 4.4)
- `ShoppingList` — id, userId, createdAt
- `ShoppingListItem` — id, shoppingListId, ingredientId, quantity, unit, checked
- `KitchenState` — singleton circle-wide row: activeRecipeId, servingsOverride, currentStepIndex,
  updatedAt (backs "Send to kitchen" and the `/api/alexa/*` surface)

## 7. Deployment

- `Dockerfile` + `docker-compose.yml` with two services: app + `postgres` (no Redis service).
- `deploy.sh` script analogous to yarg's, health check endpoint at `/api/health`.
- Migrations: `drizzle-kit migrate` runs in the container entrypoint before the app starts; the
  category seed script is idempotent and runs alongside it.
- Backups: the in-app backup export (4.9) is the user-facing path — one click, save the archive
  to Google Drive or wherever. Optionally complement it with a nightly host cron hitting the same
  endpoint (or `pg_dump` directly) for unattended copies. Test a restore once after first deploy —
  the recipe collection and photos are the irreplaceable data.
- The app Docker image includes `postgresql-client` (same major version as the `postgres`
  service) for the backup export route.
- Environment variables: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`,
  `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OPENROUTER_API_KEY` (or chosen LLM provider key),
  `YOUTUBE_API_KEY` (optional — only for the description-fetch path; transcripts via Innertube
  need no key).

## 8. Non-Goals (v1)

- No internationalization / multi-language support.
- No imperial unit conversion.
- No shared comments between circle members.
- No public/open signup (invite-code only).
- No background job queue (Redis/BullMQ) — import runs inline on request.
- No audio/video processing for YouTube import — no Whisper transcription, no multimodal
  video-understanding models; description + captions only.
- No per-step video timestamps in the UI (the `steps` schema allows them for later).
- No Alexa skill in v1 — but v1 ships its hooks (per-step `durationMinutes`, `KitchenState` /
  "Send to kitchen", `/api/alexa/*`); see §9.

## 9. Future: Alexa Companion Skill (Echo Show 15)

A voice/touch companion for following the active recipe hands-free in the kitchen. Not built in
v1, but v1 deliberately includes its hooks so the skill can be added without schema or API churn.

### 9.1 Hooks shipped in v1
- **Per-step `durationMinutes`** in the steps jsonb, extracted at import time and editable —
  timers come from data, not runtime text parsing.
- **`KitchenState` + "Send to kitchen"** — the circle-wide active recipe (with scaling and
  current step), settable from the recipe detail page.
- **`/api/alexa/*` endpoint surface** — thin, token-authenticated, JSON:
  - `GET /api/alexa/active-recipe` — active recipe, scaled ingredients, current step
  - `POST /api/alexa/step` — advance/rewind/jump `currentStepIndex`
  - `GET /api/alexa/quantity?ingredient=...` — scaled quantity lookup for one ingredient
  - `POST /api/alexa/shopping-list` — add an item by voice

### 9.2 Skill design (when built)
- **Thin skill, fat app**: all logic and data stay in the Next.js app; the skill is an
  interaction model plus a small handler that calls `/api/alexa/*`. The custom skill endpoint
  points directly at the self-hosted app over HTTPS (valid public cert already required for
  OAuth) — no Lambda, consistent with the no-extra-infra philosophy.
- **No OAuth account linking**: PIN pairing instead. On first use the skill reads out a short
  code; the user enters it in the web app, and the server maps that Alexa `userId` to the
  circle (`AlexaDevice` table — id, alexaUserId, pairedByUserId, createdAt). Everyone shares
  one collection, so per-person identity on the Echo doesn't matter.
- **Recipe selection avoids voice search** (free-form dish-name matching is unreliable):
  - "start dinner" → today's dinner slot from the circle meal plan
  - "open My Recipes" → resumes the "Send to kitchen" active recipe
  - name search is a fallback at best, never the primary path.
- **v1 intent set (keep it to ~6)**: launch/resume, start today's meal, next/previous/repeat
  step, "how much ⟨ingredient⟩?" (answered scaled), set timer from the current step's
  `durationMinutes` (Alexa Skills **Timers API**, `alerts:timers` permission), add item to
  shopping list.
- **Echo Show 15 display**: APL layout for the 15.6" landscape touchscreen — current step large,
  photo + ingredient checklist beside it, touch next/back. Mirrors the web cook-mode design.
  A "Tonight's dinner" home-screen widget is a possible follow-up.
- **Distribution**: development-mode skill only — works indefinitely on devices under the same
  Amazon account/Household; no Skill Store publication.
- **Locale** must match the language recipes are stored in, since Alexa reads step text aloud.
- **Cheap pre-validation**: before building the skill, use the web cook-mode page in the Echo's
  Silk browser to learn which voice interactions are actually missed.
